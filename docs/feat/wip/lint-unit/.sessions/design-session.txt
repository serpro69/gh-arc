  ---
  Section 1: Architecture Overview

  The feature introduces a shared runner execution engine in internal/runner/
  that both gh arc lint and gh arc unit use. This engine handles:

  - Runner discovery (from config)
  - Sequential execution with output streaming
  - Exit code tracking and result aggregation
  - Summary reporting (✓/✗ per runner)
  - --json output mode (execution metadata)

  On top of the shared engine:
  - internal/lint/ adds changed-file detection (diff vs default branch), file
  filtering, --fix support, and MegaLinter integration (deferred to v2)
  - internal/unit/ (future) wraps the engine with test-specific concerns
  (--coverage, etc.)

  The CLI layer follows the established pattern: thin cmd/lint.go that loads
  config, opens git repo, and delegates to internal/lint/.

  The changed-file detection reuses git.GetChangedFiles(base, head) where base
  is the merge-base of HEAD and the default branch (from config or
  auto-detected). A --all flag overrides to lint everything.

  ---
  Section 2: Shared Runner Engine (internal/runner/)

  The runner engine is the core abstraction. It takes a list of runner
  configurations and executes them sequentially, streaming output and collecting
   results.

  Key types:

  - RunnerConfig — unified config for both lint and unit runners: name, command,
   args, workingDir, timeout, and optional fixArgs/autoFix (lint-only fields
  ignored by unit)
  - RunResult — per-runner outcome: name, status (pass/fail/error/skipped), exit
   code, duration
  - ExecutionResult — aggregate of all RunResults, overall success bool
  - Engine — the executor. Takes []RunnerConfig + EngineOptions (json mode,
  verbose, file list for lint)

  Execution flow:

  1. For each runner: print banner (> Running <name>...)
  2. Build the command: command + args (+ fixArgs if --fix) (+ file paths for
  lint runners)
  3. Execute with os/exec, streaming stdout/stderr directly to terminal
  (preserving TTY colors)
  4. Capture exit code and duration
  5. Print per-runner summary line (✓ <name>: passed or ✗ <name>: 3 issues 
  found)
  6. After all runners: print overall summary
  7. Return ExecutionResult

  --json mode: Suppresses banners and streaming output. Collects stdout/stderr
  per runner (optional). Returns JSON with execution metadata per PAL's
  recommendation — runner name, status, exit_code, duration_ms.

  File path passing: For lint, changed file paths are appended to the runner's
  args. For unit, no file paths — args run as-is.

  Timeouts: If a runner config specifies a timeout, wrap exec.CommandContext
  with a deadline. Default: no timeout (let the tool run to completion).

  Does this engine design make sense before I move to the lint-specific and
  unit-specific layers?

● Section 3: gh arc lint — Lint-Specific Layer (internal/lint/)

  This layer wraps the runner engine with lint concerns: changed-file detection,
   file filtering, and the --fix flag.

  Workflow (the LintWorkflow orchestrator):

  1. Resolve runners. Load LintConfig.Runners from config. If empty and
  MegaLinter enabled: "true" (or "auto" + Docker detected) → MegaLinter runner
  (v2). If nothing → print guidance message, exit 0.
  2. Detect changed files. Find the merge-base between HEAD and the default
  branch (git.GetMergeBase(defaultBranch, "HEAD")), then
  git.GetChangedFiles(mergeBase, "HEAD"). If --all flag, skip this and pass no
  file paths (runner lints everything).
  3. Filter files. Remove deleted files (can't lint them). Optionally filter by
  file extension if a runner declares which extensions it handles (future — not
  in v1).
  4. Convert runner configs. Map config.LintRunner → runner.RunnerConfig,
  injecting fixArgs when --fix is active.
  5. Execute. Call runner.Engine.Run() with configs + changed file paths.
  6. Return results. Propagate ExecutionResult to the CLI layer.

  CLI flags (cmd/lint.go):
  - --fix — enable auto-fix mode (appends fixArgs to each runner)
  - --all — lint all files, not just changed ones
  - No positional args (enforced with cobra.NoArgs per the review finding)

  Exit codes:
  - 0 — all runners passed
  - 1 — one or more runners reported issues (non-zero exit)
  - The command never exits >1 for lint findings — the distinction between "lint
   issues" and "runner crash" is the runner's exit code, which is reported in
  the summary

● Section 4: gh arc unit — Test-Specific Layer (internal/unit/)

  Simpler than lint since there's no file scoping or fix mode.

  Workflow (the UnitWorkflow orchestrator):

  1. Resolve runners. Load TestConfig.Runners from config. If empty → print
  guidance message (similar to lint's), exit 0.
  2. Convert runner configs. Map config.TestRunner → runner.RunnerConfig. The
  Timeout field on TestRunner gets parsed (e.g., "5m" → time.Duration) and set
  on the RunnerConfig.
  3. Execute. Call runner.Engine.Run() with configs, no file paths.
  4. Return results.

  CLI flags (cmd/unit.go):
  - No special flags in v1. --coverage is a natural future addition.
  - No positional args (cobra.NoArgs)

  Same exit code strategy as lint: 0 for all pass, 1 for any failure.

  The key difference from lint: No changed-file detection, no --fix, no --all
  flag. Just run the configured test runners and report results. The value is in
   the consistent execution framework, status reporting, and --json output — not
   in scoping.

  ---
  Section 5: Config Changes

  The existing config types need one addition:

  - LintRunner: Add FixArgs []string field (mapstructure:"fixArgs") — args
  appended when --fix is active
  - JSON schema: Add fixArgs to the lintRunner definition
  - TestRunner: No changes needed — the existing fields (name, command, args,
  workingDir, timeout) are sufficient

  The autoFix bool on LintRunner becomes the per-runner opt-in: if autoFix: 
  false (default), the runner skips fix mode even when --fix is passed globally.
   This gives users per-runner control.
